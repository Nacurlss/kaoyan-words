| 12 | **隐藏 0 次释义** | 与真题 POS 不匹配的释义不再显示 (0次) |
| 13 | **常考例句列** | 表格第 3 列显示最高频释义的例句（截 60 字符） |
| 14 | **variants 小写归一化** | 词形变体统一小写，Law 和 law 不重复 |
| 15 | **释义去英文例句** | 墨墨词库释义字段清洗，只留中文解释 |
| 16 | **真题句子截取** | 点击次数弹窗显示短句（非整段），sent_tokenize 切句 |
| 17 | **例句目标词加粗** | 弹窗中目标单词用 `<span class="highlight">` 包裹 |

### ⚠️ 有残缺（5 项）

| # | 功能 | 问题 | 建议 |
|---|------|------|------|
| 1 | **真题格式验证** | 1986-2024 的真题整理 TXT 是否每一年都正确分段/换行/划分题型，从未逐份检查过 | 选 3 个关键年份（1986/2005/2017）打开 TXT 看段落是否完整 |
| 2 | **例句截取精度** | sent_tokenize 对中英混排、题号开头句可能切错（如把 `1. The court` 切成两句） | 抽查 10 个单词的弹窗例句，标记切错的情况 |
| 3 | **释义清洗彻底性** | 墨墨词库的 `_clean_meaning` 在 build_vocab.py 和 analyzer.py 两处各做了一次，但没有重建词库再验证 | 重跑 `python scripts/build_vocab.py` 后抽查 20 个词的释义 |
| 4 | **高频词数量过低** | 清洗说明/选项后，默认阈值（高频≥0.5）下表里可能一个高频词都没有 | 把高频线降到 0.3 试试，或改用"按年份出现比例"而非 section 比例 |
| 5 | **联网词典缓存** | `dictionary.py` 已有 httpx 异步框架，缓存文件 dict_cache.json 存在但命中率和更新逻辑不明 | 确认缓存是否正常工作，缺词时是否回退到墨墨词库 |

### ❌ 完全缺失（6 项）

| # | 功能 | 为什么该做 |
|---|------|-----------|
| 1 | **数据持久化** | 现在刷新页面或重启服务，所有导入的试卷和设置全部丢失。每次都要重来 |
| 2 | **按题型分频统计** | 阅读高频词和完形高频词是两回事。"law 在阅读里出现 10 次"比"law 总共出现 15 次"更有学习价值 |
| 3 | **生词本导出** | 用户筛选出一批要背的词后，不能导出到墨墨或 Anki 格式 |
| 4 | **单词学习进度追踪** | 没有"已学/未学/掌握/生疏"标记，不能做成间隔复习 |
| 5 | **全文搜索** | 只能搜单词本身，不能搜中文释义、不能看单词在原文中的完整上下文 |
| 6 | **用户自定义词表** | 界面提示可以创建 custom.txt 但没给入口，用户不知道怎么加自己的排除词 |

## 第二部分：可复用产品流程 checklist

> 以后做任何个人项目都能拿来一步一步 check。

### 阶段 1 · 构思（1-3 天）

**干什么**：把模糊想法变成一句话的产品定义 + 3 个核心用例。

**在 AI coding 里怎么做**：
```
我有个想法：[一句话描述]。
帮我做三件事：
1. 这个想法的核心用户是谁，痛点是什么
2. 写出 3 个最重要的使用场景（谁、做什么、期望什么结果）
3. 这个产品的最小可用版本（MVP）应该只包含哪 3-5 个功能
```

**要问自己的问题**：
- 这个问题我自己有没有？我是不是那个用户？（自己做用户 → 验证最快）
- 市面上有没有现成工具？如果有，为什么我还要自己做？（差异化在哪）
- 做完后一周内我还会用它吗？（如果不会 → 可能不值得做）

**产出物**：一个 `Problem.md` 文件，包含一句话定义 + 3 个场景 + MVP 功能清单

### 阶段 2 · 原型验证（1-5 天）

**干什么**：把 MVP 做成一个能跑的东西，自己用一下看看方向对不对。

**在 AI coding 里怎么做**：
```
现在我要做 MVP，包含以下功能：[列出 3-5 个]。
请给我：
1. 项目目录结构
2. 核心数据模型
3. 最简 API/界面
不要做任何"加分项"功能，不要美化 UI，只要核心逻辑能跑通。
```

**要问自己的问题**：
- 我用了一遍，觉得有用吗？（没感觉 → 停下来，别继续投时间）
- 最卡顿/最难用的一个地方是什么？（记下来，下个版本修）
- 数据从哪来？是手动录入还是自动抓取？（手动超过 10 分钟 / 次 → 必须自动化）

**产出物**：一个能本地运行的 MVP（哪怕命令行/单页面），+ 一个 `v1 计划.md` 记录第一版做了什么

### 阶段 3 · 构建迭代（按周滚动）

**干什么**：在 MVP 基础上加功能、修体验、补数据。每次只做一小批改动，做完就验证。

**在 AI coding 里怎么做**：
```
当前项目状态：[简述].
我要做这一批改动：[列出 3-8 条]。
请先写一个修复/开发计划——每条改动涉及哪些文件、怎么改。
确认计划后，逐条执行。
```

**要问自己的问题**：
- 这批改动里哪个最影响使用体验？（排最优先）
- 改完一个功能后我有没有实际跑一遍看效果？（别只信 AI 说"改好了"）
- 这个版本和前一个版本比，用户能感知到的变化是什么？（没有 → 这批改动可能不需要）

**产出物**：每次迭代一个 `vN 计划.md`，包含改动清单 + 执行记录

### 阶段 4 · 测试修复（穿插进行）

**干什么**：三类检查——功能验收、数据质量、边界情况。

**在 AI coding 里怎么做**：
```
现在检查当前版本：
1. 导出一份完整数据（如 Excel），抽查 10 条看是否合理
2. 用几个极端输入测试（空文件、超大文件、特殊字符）
3. 列出所有和预期不符的地方

然后帮我分析每个问题的根因，提出修复方案。
```

**要问自己的问题**：
- 如果我是一个新用户第一次打开，能完成核心操作吗？（自己走一遍）
- 数据有没有"污染"？（比如说明文字混进统计、空值没处理）
- 最坏情况下会不会崩？（上传 100 个文件、输空搜索、断网）

**产出物**：一个 `Bug 清单`（或直接写进 Problem.md），每修一条划掉一条

### 阶段 5 · 交付（选做）

**干什么**：决定要不要给第二个人用。

**在 AI coding 里怎么做**：
```
这个项目现在可以给第二个人用了。
帮我：
1. 写一个 5 分钟能看懂的使用说明
2. 打包成别人也能一键启动的形式
3. 列出"别人可能遇到的前 5 个问题"及解决方法
```

**要问自己的问题**：
- 我要给谁用？（自己 → 不需要交付；朋友/同学 → 简单文档即可；公网 → 需要部署）
- 别人不需要懂代码就能跑起来吗？（需不需要装 Python/Node、配环境变量）
- 我还会继续维护吗？（不会 → 标记"个人工具，不承诺维护"）

**产出物**：一个 `使用手册.md` + 一个 `start.sh`（或 Dockerfile）+ GitHub README

### 阶段 6 · 持续运维（长期）

**干什么**：数据更新、修 bug、小功能追加。节奏是"发现问题 → 修 → 记录"。

**在 AI coding 里怎么做**：
```
当前项目有以下问题：[列出].
帮我排优先级，每个问题估计影响面。
然后从最高优先级开始修，修完一个验证一个。
```

**要问自己的问题**：
- 这个项目我最近一个月还在用吗？（不在用了 → 归档，别浪费精力）
- 新加的功能会不会让原来的功能变复杂？（会 → 考虑拆分或做开关）
- 有没有定期导出/备份数据？（数据丢了比功能坏了更致命）

**产出物**：持续更新 `Problem.md`，每次修复写简短记录

## 第三部分：用本项目走一遍流程（案例复盘）

### 阶段 1 · 构思 → 本项目实际情况

**✅ 做了什么**：
- 需求非常清晰：自己是考研用户，知道"真题词频"有价值，市面上墨墨只给大纲词不给频率统计
- 数据源现成：47 年真题在手、墨墨 PDF 在手
- 一句话定义：*统计 47 年考研英语真题中每个单词出现频率，按高/中/低分级，关联墨墨释义*

**⚠️ 踩了什么坑**：
- 一开始没写 Problem.md，需求全在脑子里。v1 做到一半才发现"统计单位用文件名不对，同一年的多个 section 要分开计数"
- 没有明确"不做的事"——比如 WSD（词义消歧）要不要做？墨墨没收录的词要不要联网查？这些边界模糊导致后期频繁返工

**💡 重来怎么改**：
- 第一天就写一个 `Problem.md`，列出 MVP 要什么 + 明确不要什么
- 先用手工验证：拿 2017 年的一份真题，手动统计 10 个单词的出现次数，再和程序结果对比——如果对不上，说明统计逻辑有根本缺陷，先别往下做

### 阶段 2 · 原型（v1）→ 本项目实际情况

**✅ 做了什么**：
- `build_vocab.py` 从墨墨 PDF 提取词库 → 落盘 6 个 JSON
- `section_splitter.py` 题型切分 → 真题整理/ 目录
- `analyzer.py` NLTK POS 标注 + 词形还原 + 四元组统计
- `main.py` FastAPI 后端 + 前端 WordTable 表格展示
- `start.sh` 一键启动

**⚠️ 踩了什么坑**：
- MVP 时跳过了 1986-2009 合订本（DOCX），想着"v2 再做"。结果 v1 只能看 2010-2025，数据量不够，频率统计代表性差
- 墨墨 PDF 解析遇到大量"跨页释义归属错位"——页码分隔把一句话拆成两半，buffer 逻辑写了很久
- 没在 MVP 阶段验证"释义是否正确关联到单词"——v3 才发现释义里混进了英文例句

**💡 重来怎么改**：
- MVP 阶段就至少覆盖全量真题（哪怕文本质量粗糙），而不是只做 16 年
- 原型做完第一件事：导出 CSV，人工抽查 50 个单词的释义和例句，错误率超 10% 就停下来修数据质量

### 阶段 3 · 构建迭代（v2 + v3）→ 本项目实际情况

**✅ 做了什么**：

v2：
- 导入 1986-2009 合订本（DOCX 年份切分 + 表格提取）
- 修复段落塌成单行 → 保留空行结构
- 隐藏 count=0 的释义
- 新增常考例句列

v3：
- variants 小写归一化
- 释义去英文例句
- 例句切句 + 目标词加粗
- 常考例句精准化（最高频释义最短句）
- 墨墨例句开关
- 列顺序重排 + "频率"→"年频率"

**⚠️ 踩了什么坑**：
- v2 的 DOCX 合订本处理异常复杂 —— 三个 DOCX 格式差异大，早期年份（1986-1990）题型排布和后期完全不同
- "修复段落塌成单行"改 `_extract_sentences` 时，影响了已有的 2010-2025 数据（修复一个引入另一个）
- v3 改了 8 个文件，改动太散，验证时很难判断"是哪个改动导致的异常"

**💡 重来怎么改**：
- 每次只改一个模块，改完就跑 `./start.sh` 验证。不要一口气改完 8 个文件再测试
- DOCX 合订本应该在 v1 时就作为一个独立问题先解决，而不是等到 v2 和段落修复混在一起
- 每个迭代结束时导出 CSV，和前一个版本对比 —— 哪些词的频率变了、为什么变

### 阶段 4 · 测试修复（v4）→ 本项目实际情况

**✅ 做了什么**：
- 发现"频率最高的词是 sheet"——因为 `ANSWER SHEET` 每年都出现
- 清洗 Directions / ANSWER SHEET / [A][B][C][D] 选项 / 题干
- 过滤 PDF 粘连词（`theanswersheet` 等）
- 修复 start.sh 的 Python 版本选择 + 监听地址
- 修复后导出体积从 500KB → 64KB

**⚠️ 踩了什么坑**：
- 清洗来得太晚了。v1-v3 一直在加功能，但没停下来问"我现在统计出来的数据是对的吗？"——如果 v1 就导出 CSV 看一眼，不会到 v4 才发现 sheet 是高频词
- 清洗改了三处（section_splitter、main.py 启动加载、analyzer 索引构建），逻辑分散——以后改一处可能忘了改另外两处
- 本机 `python3` 是 3.9，代码用了 3.10+ 语法（`str | None`），start.sh 没做版本检测直接挂了

**💡 重来怎么改**：
- 数据验证应该和原型一起做，而不是等 3 轮迭代后再修
- 清洗逻辑集中在 section_splitter 一个文件，main.py 和 analyzer.py 只调用它
- 首次启动脚本就检测环境（Python 版本、NLTK 数据、端口占用），不等到出 bug 才发现

### 阶段 5 · 交付 → 本项目实际情况

**✅ 做了什么**：
- 写了完整的使用手册（186 行），覆盖启动、界面、操作、常见问题
- `start.sh` 一键启动对非技术用户友好
- `CLAUDE.md` 项目配置让 AI 助手理解项目规则

**⚠️ 踩了什么坑**：
- 没有做数据持久化 —— 刷新页面就丢失，这决定了目前只能自己用（因为自己知道要重新导入）
- 没有做"打包"——别人要跑需要装 Python 3.11 + Node.js + 一堆依赖，门槛高
- 没有标"哪些功能不稳定"——用户可能以为例句都是对的

**💡 重来怎么改**：
- 交付前先找一个非技术同学试着跑一遍，看他能不能独立完成"启动 → 导入 → 导出"
- 使用手册里加一个「已知问题」章节，标出精度局限
- 至少做 SQLite 本地存储，让刷新不丢数据

### 阶段 6 · 持续运维 → 本项目实际情况

**当前状态：尚未正式进入这个阶段。** v4 刚做完，项目还处于"自己用"的状态。

**进入运维后要做的事**：
- 2026 年真题出来后更新数据
- 定期验证数据质量（防止静默退化）
- 有用户反馈后按缺口清单排优先级

## 第四部分：思维拓展

> 以下概念不需要每个都照着做。了解即可，用到的时候知道"有个东西叫这个"。

### 一、敏捷开发 & Scrum（为什么你已经在用了）

你现在的 4 轮迭代（v1→v4）本质上就是敏捷开发，只是没叫这个名字。

| 概念 | 你在本项目中的等价物 | 一句话 |
|------|---------------------|--------|
| **Sprint（冲刺）** | v1/v2/v3/v4 每一轮 | 固定周期（你的是 1-2 天）内完成一批改动 |
| **Backlog（待办清单）** | Problem.md | 所有要做/要修的事的列表，排优先级 |
| **站会（Daily Standup）** | 你每次打开终端问自己"上次做了什么、今天做什么、有什么卡住" | 15 分钟，只同步状态不讨论方案 |
| **回顾（Retrospective）** | 工作日志里的"踩了什么坑 + 重来怎么改" | 每轮结束后问：什么做得好、什么做得差、下轮怎么改 |
| **MVP（最小可用产品）** | v1 的核心功能 | 只做能验证想法的最少功能 |

**你在 AI coding 里可以这样用 Scrum**：
- Sprint 开始：把 Problem.md 里的条目拉 3-5 条到本轮计划
- Sprint 中：每改完一个文件就验证一次
- Sprint 结束：导出数据看一眼 + 写简短复盘

### 二、SDL 安全开发生命周期（什么时候要考虑）

SDL 的核心思想：**安全不是在最后"加一层保护"，而是从设计阶段就嵌入。**

| 阶段 | 要问自己的问题 | 本项目的例子 |
|------|---------------|-------------|
| **设计** | 数据从哪来、存哪、谁能访问？ | 墨墨词库是公开 PDF → 没问题；用户上传的 PDF 可能含敏感内容 → 当前存本地，OK |
| **实现** | 输入有没有校验？ | 上传文件只接受 .docx/.pdf → 已做。但文件大小无限制 → 可以加 |
| **验证** | 有没有已知漏洞的依赖？ | NLTK、FastAPI 等注意看版本是否有 CVE |
| **发布** | 服务监听在哪？谁可以访问？ | v4 改成了 127.0.0.1 → 只本机访问，正确 |
| **运维** | 依赖过期了怎么办？ | `pip install --upgrade` 定期跑一下 |

对于个人项目，你只需要记住：**不要暴露端口到公网、不要提交密码/token 到 git、定期更新依赖。**

### 三、PRD 和 MRD（什么时候写、什么时候不写）

| 文档 | 全称 | 回答什么问题 | 本项目需要吗？ |
|------|------|-------------|---------------|
| **MRD** | Market Requirements Document | 市场有多大、竞品有哪些、目标用户是谁 | **不需要。** 你是唯一的用户，不存在"市场" |
| **PRD** | Product Requirements Document | 产品具体做什么、每个功能怎么交互、验收标准是什么 | **需要，但不用写成大文档。** 你的 v1 计划 + Problem.md + 使用手册 合在一起就是一份够用的 PRD |

**自己做项目的 PRD 最低配版**：
```
1. 一句话定义（这个产品干什么）
2. 3 个核心场景（谁、做什么、期望什么结果）
3. MVP 功能清单（第一版做什么）
4. 不做的事（明确边界，防止范围蔓延）
5. 验证方法（怎么判断做好了）
```

**你在本项目已经有的就是这些** —— v1 计划写了目标 + 设计决策，Problem.md 列了待修问题，使用手册写了交互。只不过没有整理成一个单独文档。如果以后要给别人看，把这三样合成一个就行。

### 四、额外一提：Dogfooding（吃自己的狗粮）

你现在的模式其实有一个名字叫 **Dogfooding**：

> 自己做的东西自己先用，用出问题来再修，修完后体验提升就是真实需求。

这是个人项目最有效的验证方式——因为你自己就是目标用户，不需要做用户调研、不需要做 A/B 测试，用得爽不爽你自己知道。
